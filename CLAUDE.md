# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A cross-platform (iOS/Android/macOS/Windows/Linux) Flutter workout-tracking app. The Flutter app lives in `tracker/`; the repository root also contains a PowerShell script for running GitHub Actions locally. This is an early-stage work in progress - much of the UI is placeholder scaffolding.

## Architecture layout (Flutter app-architecture case study)

`tracker/lib/` follows the official Flutter [app architecture case study](https://docs.flutter.dev/app-architecture/case-study#package-structure) (MVVM + Repository, hybrid organization: data/domain by type, UI by feature):

- `lib/domain/models/` - Isar-annotated models (`Exercise`, `Gym`, `WorkoutSession` + embedded `WorkoutSet`, `WorkoutSplit` + embedded days/items, `Muscle`/`MuscleGroup`, split templates) plus pure value types (`graph_config.dart` - a `GraphConfig` is one exercise and a `GraphMetric`: estimated 1RM, 1RM PR, heaviest weight or volume; `GraphTimeframe` is the range all graphs share, `weight_unit.dart`, `number_entry.dart`, `effort_scale.dart` - RPE / RIR, sets store RPE and RIR reads as 10 minus it, `split_draft.dart` - the editable `SplitDraft`/`DayDraft`/`ExerciseDraft`/`SetTarget` copy of a split whose days and exercises remember their saved position, and whether they were dragged; a `SetTarget` is a working set or a warm-up; `session_draft.dart` - the editable `SessionDraft`/`SetDraft` copy of a past workout, each set remembering the saved set it came from, `applyTo` writes it over the saved one and keeps its id and split day). Generated `*.g.dart` parts live next to their parents.
- `lib/domain/services/analytics.dart` - pure, DB-free analytics engine (`normalizedWeight`, `epley1rm`, `exerciseBest1rm`, `volumeTrend`, `estimateGymMultiplier`, ...). Imports only domain models.
- `lib/domain/services/graph_series.dart` - what one graph plots (`graphSeries` -> `GraphSeries`): its sessions in range (each with its value, the best so far, whether it was a record, the set behind it), the best before the range, and for volume the weeks (1M, 3M) or months (1Y, All) as `GraphBucket`s, empty ones included; ranges count calendar months back from today (`graphRangeStart`), never from the newest session; `latest`, `change`, `headlineBucket` and `average` are what its headline reads.
- `lib/domain/services/` also holds the pure workout planning helpers: `split_rotation.dart` (`upNext`, `currentSplitOf`: the day due next from `SplitDayVisit`s, which carry the session's length; `lastVisitOf`; `splitsByLastUsed`: the Splits tab order), `set_prefill.dart` (`PreviousPerformance` with its `topSet`, `ghostForRow`: placeholder values for pending set rows) and `split_diff.dart` (`diffSplit`: every saved-vs-draft change, worded for the review sheet; a move names the item that was dragged, never the neighbour it passed). For History: `workout_dates.dart` (`WorkoutDateIndex`: start times newest first, resolved lazily per month and per list position, so the month headings, their counts, a day's first workout and the streak never cost O(history) up front; `CalendarGrid`), `session_summary.dart` (`groupByExercise`, `topSetOf`: the best set, `workingVolumeOf`, `workingSetCount`, `exercisePreview`, `setCountsLabel`) and `session_changes.dart` (`sessionChangeCount`: one per field and per set edited, added or removed, ratings and set types included; `isEditedSet`, `savedSetOf`).
- `lib/data/repositories/` - one file per repository (`ExerciseRepository`, `GymRepository`, `WorkoutSplitRepository`, `WorkoutSessionRepository`) plus the `TrackerRepository` facade. Pages/cubits never touch Isar directly.
- `lib/data/services/` - `db.dart` (single Isar instance, opened only by `main.dart`), `seed.dart` (first-run exercise seeding), `sample_data.dart` (`seedSampleData`: fourteen months of training up to now, deterministic for a given day: the library, two gyms (one at a 0.9 multiplier), Push Pull Legs (current) after Upper Lower, warm-ups, RPE, a two-week break, free workouts) and `test_mode.dart` (`TestMode`: the on/off flag file in the documents dir, `openSandbox` (a fresh, seeded Isar under the temp dir with its own name, since Isar has no in-memory mode) and `closeSandbox` (deletes it); `MemoryStorage`, the in-memory `Storage` test mode's cubits save to).
- `lib/ui/core/ui/` - shared widgets/helpers used across features: `CustomAppBar`, `pushTo` (`custom_route.dart`), `MaxWidth`, `GraphChart` (`graph_chart.dart`: a `GraphSeries` drawn in ink by a `CustomPainter`, no chart package: a line of each session with a wash under it, a staircase of bests over faint session dots with records ringed, or columns per week or month with the running one light and the average as a hairline; `compact` drops the axes for a tile; a tap, a drag or a hold reads the nearest point, which stays read until tapped again, and hovering reads too; the line ahead of the point read steps back; it lays out from its box size in paint, never in build, so tile rows can share an intrinsic height), `weight_format.dart` (kg/lb UI conversion), `repository_scope.dart` (`RepositoryScope` InheritedWidget exposing `TrackerRepository` down the tree), `AccentButton`, `SheetSurface`, `ItemCard` (`item_card.dart`: rows in an outlined card, each inset 4 px so a selected or pressed highlight never touches a divider; Settings pages and every bottom sheet's list of rows use it), `EditSheet` (`edit_sheet.dart`, opened with `showEditSheet`: every value is edited in a bottom sheet with one Save-style button, swiping it away cancels; dialogs (`AppDialog`, `showConfirmDialog`) only ask to confirm), `SwipeToDelete` (raw-pointer, 2-step swipe for rows full of text fields: the first swipe opens the row on Delete, a second swipe or a tap on Delete removes it; `SwipeToDeleteChip` is the same for grid tiles: the first swipe arms a red trash tile, the second deletes; a chip inside a swipe row keeps the swipes that start on it), `Peek` (`peek.dart`: a card shown beside a row in its tab's overlay, below or above it, modal with the page dimmed around the row or pointer-transparent for hover), `SlidingColumn` (keyed children slide to their new places when the order changes), `AnimatedReveal` (a child that comes and goes with a state grows in and shrinks away, keeping its last content while it leaves), `keyboard_inset.dart` (`keyboardClearanceOf`: the bottom room a page's scrollable leaves for the keyboard; `KeyboardReveal`, wrapped around the app in `MyApp`, scrolls the focused field above the keyboard without rebuilding anything, so nothing may rebuild the app per keyboard frame, e.g. a theme derived from the inset; hidden tabs see the keyboard as down), `test_mode_scope.dart` (`TestModeScope`: whether test mode is on, `setEnabled`, `reset`; absent in tests; `TestModeBanner`: the ink strip over every screen while it is on), `relative_dates.dart` (`dayLabel`, `agoLabel`, `lengthLabel`, and the date style History reads in: `shortDateLabel` "Mon 9 Nov", `dateTimeLabel` "Mon 9 Nov, 18:04", `timeRangeLabel` "... to 19:16", `monthLabel`, never ISO dates), `effort_format.dart` (`effortScaleOf`, `effortLabel`: a stored RPE on the chosen scale), `effort_sheet.dart` (`showEffortSheet`: 0 to 10), `effort_strip.dart` (`EffortStrip`: the open set row's one-tap rating), `number_keypad.dart` (`NumberKeypad`, `KeyboardToolbar`, `applyKeypadKey`), `slide_up_panel.dart` (`SlideUpPanel`: the keypad's slide), `plan_bar.dart` (`PlanBar`: the workout as one bar; `ink: true` draws a finished one), `set_badge.dart` (`SetBadge`: a set's number or a dashed W), `draft_tag.dart` (`DraftDot`, `DraftTag`: the amber unsaved marks). Each of the keypad, toolbar, effort sheet and strip, and the gym sheet takes `live: false` to draw in ink instead of blue where nothing is live (History). `lib/ui/core/themes/accents.dart` (`TrackerAccents`) adds the only two accents on top of the neutral Forui theme: blue = a live workout, the actions that start or restore one, and the selected bottom-nav tab; amber = unsaved edits (a split's draft, a past workout's draft). A finished workout is drawn in ink.
- `lib/ui/core/themes/material_theme_bridge.dart` - Forui `FThemeData` -> SDK `ThemeData` bridge + nav-label strengthening (`strengthenNavLabels`: readable labels at rest, the selected tab in the blue accent).
- `lib/ui/<feature>/widgets/` + `lib/ui/<feature>/view_models/` - features: `feed`, `history`, `workout` (incl. `view_models/workout_cubit.dart`), `splits` (incl. `view_models/split_drafts_cubit.dart`), `exercises`, `settings` (incl. `view_models/settings_cubit.dart`), `analytics` (incl. `view_models/analytics_data.dart`).
- `lib/routing/` - `app_session.dart` (`AppSession`: the repository and the three app-wide cubits, real or test mode's; a switch or reset rebuilds the whole app under a new key with `HydratedBloc.storage` swapped first, so nothing of one leaks into the other; test mode's settings start from the real ones with the sample split current and five graphs; the old sample database is closed and deleted after the frame), `home_page.dart` (5-tab shell with nested `Navigator`s) and `tab_navigation.dart` (`TabName`, `HomePageSingleton`, `TabVisibilityScope`); features depend on `tab_navigation.dart`, never on the shell.
- `lib/utils/` - pure Dart helpers (`form_validators.dart`).
- `lib/main.dart` - composition root: HydratedBloc storage, Isar open + seed, test mode's sample database when its flag is on (dev builds only), `AppSession` (`RepositoryProvider`/`RepositoryScope`/`MultiBlocProvider` wiring), and `MyApp`, whose builder puts `TestModeBanner` over every screen.

Layer direction: `ui` -> `data` + `domain`; `data` -> `domain` (+ Isar); `domain` depends on nothing UI/data. Intra-`lib` relative imports are lint-legal but package: imports are preferred for cross-folder references.

## Commands

The Dart/Flutter app is rooted in `tracker/`; run Flutter/Dart commands from that directory.

```bash
# Install dependencies
cd tracker && flutter pub get

# Static analysis (this is what CI runs)
cd tracker && flutter analyze

# Run tests (single: `flutter test test/app_test.dart`)
# Domain/unit tier (pure Dart, no Isar/DB): `flutter test test/domain`
cd tracker && flutter test

# Regenerate code from Isar/JsonSerializable annotations
cd tracker && dart run build_runner build
```

**Commit messages.** All commits (from agents and human contributors
alike) MUST follow [Conventional Commits](https://www.conventionalcommits.org/):
`type(scope): description`. Allowed types: `feat`, `fix`, `docs`, `style`,
`refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`; `scope` is
optional (e.g. `feat(workout): add warmup set toggle`, `fix: clamp chart
height`). Subject is lowercase, imperative, no trailing period.

**Git hooks.** Husky (Dart package on pub.dev, not npm) runs a `pre-commit`
hook that formats code with `dart fix --apply` then `dart format .`. The
hook lives at repo-root `.husky/pre-commit` (committed, so it's
project-specific); git runs it because `core.hooksPath` points at `.husky`
(already set here; a fresh clone needs the one-time
`git config core.hooksPath .husky`). Cross-platform: `husky` is pure Dart
and the plain-`sh` hook is LF-pinned via `.gitattributes`
(`.husky/** text eol=lf`) so Windows CRLF autoconversion can't break it on
any of Windows / macOS / Linux.

Tests live under `tracker/test/`, mirroring `lib/`: `test/domain/` (analytics, split templates), `test/utils/` (form validators), `test/data/` (Isar repositories/CRUD), `test/ui/<feature>/` (cubit state/flows, page widgets), plus `test/app_test.dart` (app shell). Shared test infrastructure lives in the top-level `tracker/testing/` directory (sibling of `test/`, imported via relative paths): `test_helpers.dart` (Isar core init, temp Isar open, `pumpApp`, watcher polling), `test_fixtures.dart` (seed data shared with the sweep tests), `test_fonts.dart` (loads Inter/Lucide/MaterialIcons/Roboto from the pub cache and Flutter SDK - the test env ships no real fonts), `screenshot_helpers.dart` (PNG capture + manifest), and `fakes/in_memory_storage.dart` (in-memory `HydratedBloc` `Storage` fake). CI (`dart.yml`) runs dependency installation, `flutter analyze`, generated-code verification, generated-file drift detection, and `flutter test` on `ubuntu-latest`.

## State management & persistence

- **Isar** for local persistence; **Bloc (flutter_bloc + HydratedBloc)** for state management. The case-study MVVM layout treats each `HydratedCubit` as its feature's view model (`ui/<feature>/view_models/`).
- `WorkoutCubit` (`lib/ui/workout/view_models/workout_cubit.dart`) is the sole workout cubit, a `HydratedCubit<WorkoutState>` - state is JSON-serialized via `HydratedStorage`, so the in-progress workout survives app restarts. `WorkoutState` is a hand-written plain class with manual `toJson`/`fromJson` holding `isInProgress`, `startTime`, gym id/name, optional plan (`planTitle` = the day + `List<PlanExercise>`), the split link (`splitTitle`, `splitId`, `splitDayIndex`, written to the saved session for the Up next rotation), `nextGymId` (a gym picked for the next workout only; null starts it at the home gym, and starting a workout uses the pick up), `lastSetAt` (when the last set was logged: the rest clock), and `List<ActiveSet> sets`; `ActiveSet.isWarmup` flags `SetType.warmup` and `ActiveSet.rpe` holds the set's rating. `startWorkout`/`startPlanWorkout` begin a session; a free workout (`planTitle == null`) builds its `plan` one card at a time via `addExercise`/`removeExercise`; `logSet`/`updateSet`/`removeSet`/`setRpe` mutate the set list; `reorderExercise` reorders the cards; `setGym` moves the running session (the next one still starts at home), `pickNextGym` picks the gym for the next start; `endWorkout` (async) writes a real `WorkoutSession` to Isar via its optional `TrackerRepository` reference, then resets to idle. It also estimates gym multipliers (`estimateGymMultiplier`) at end-of-workout.
- `SettingsCubit` (`lib/ui/settings/view_models/settings_cubit.dart`) is a `HydratedCubit<SettingsState>` for the weight unit, the logging prefs (`prefillSets`, `numberEntry`: keypad / phone keyboard / steppers, `effortScale`: RPE / RIR, `showHeavyWeightWarning`), the rep target new planned sets start at (`defaultRepMode` + `defaultReps` / `defaultRepRange*`, set at once by `setDefaultSetTarget`), `currentSplitId` (the split Up next trains from; null follows the last trained), `splitsUsedAt` (when splits stopped being current; with training times it orders the Splits tab) + user graphs (`graphs`, `addGraph`/`updateGraph`/`removeGraph`) and the range they all show (`graphRange`, `setGraphRange`; 3M by default). Its pure value types (`GraphMetric`, `GraphTimeframe`, `GraphConfig`, `WeightUnit`, `NumberEntry`, `EffortScale`) live in `lib/domain/models/{graph_config,weight_unit,number_entry,effort_scale}.dart`.
- `SplitDraftsCubit` (`lib/ui/splits/view_models/split_drafts_cubit.dart`) is a `HydratedCubit<SplitDraftsState>`: every Splits tab edit lands at once in a per-split draft (`SplitDraftEntry`: the saved `base` editing started from + the edited `draft`) that survives app restarts; `save` writes it to Isar, `discard` drops it, and an edit that brings the draft back to its base drops the entry.
- `WorkoutCubit` is provided app-wide in `main.dart` via `MultiBlocProvider` with `lazy: false`.
- The **`.g.dart` files are generated** - do not edit them by hand. After changing a `@collection`/`@embedded`/`@enumerated` annotation, run `dart run build_runner build` in `tracker/`. The analyzer excludes `*.g.dart`. (Isar 3.1 requires `@enumerated` enum fields to be non-nullable and models must not carry computed getters - the generator rejects both.)
- Host-side `flutter test` needs the Isar native lib: `libisar.dylib` is copied into `tracker/` (gitignored) so tests load it.
- **Isar schema is frozen pre-1.0**: additive changes only (no renames/deletes); the current schema and freeze rules live in `docs/ISAR_SCHEMA.md`, the isar_community stay/escape-hatch decision in `docs/adr/0001-isar-community.md`.
- **Hydrated payloads are versioned**: `WorkoutState` (v4)/`SettingsState` (v3: adds `graphRange`; graphs without an exercise, from the old "All exercises" option, are dropped on read)/`SplitDraftsState` (v1) JSON carries a `'v'` field; `fromJson` dispatches to `_fromV1`-style parsers and unknown versions fall back to safe defaults. Extend per-version parsers on shape changes, never loosen casts.
- **AppLog** (`lib/data/services/app_log.dart`) is the local ring-buffer logger (mirrors to `tracker.log` in the documents dir); all app-level error channels in `main.dart` (run-zone, Flutter, platform dispatcher, build-error widget) route through it. `APP_ENV=prod` (dart-define, `lib/data/services/app_env.dart`) gates dev affordances and verbose logging.

## UI features (lib/ui/<feature>/)

- **feed** - `FeedPage` streams recent completed sessions (loading/empty/error states), hosts the Analytics section (the range control, then the graphs as half-width `GraphTile`s in a `GraphGrid` with a dashed Add graph tile; a tap opens the graph's `GraphPage`) and links to `SessionDetailPage`; Settings is reached from the Feed app-bar action.
- **history** - History keeps everything: it shows past workouts, restores one, and fixes a mistake in one; deleting is never one tap away. `HistoryPage` is one list, newest first, under month headings (the year when not this one) with their workout count; a row is the date gutter (weekday over day), the title over a one-line exercise preview ("Bench press, Overhead press and 3 more"), and the length over the working set count; a tap opens the past workout, nothing else (no swipe, no menu). It reads synchronously and lazily: the first frame reads ids and start times only (`WorkoutSessionRepository.getTimelineSync`, two property queries, into a `WorkoutDateIndex`), rows sit in a `SliverVariedExtentList` with heights known from the text size, and sessions (with their exercise names, `ExerciseRepository.getTitlesSync`) are read a page of 24 at a time as rows are built (`getByIdsSync`). It reloads on `repo.sessions.watchChanges()` (deferred while its tab is hidden). The app-bar calendar button opens `showHistoryCalendar` (`calendar/history_calendar.dart`: the months are the pages of a carousel that follows the finger, each page a month's name and workout days, its days of the week and its grid, so all of it travels together, and what belongs to no one month, the streak and the way back, stays still under it; there are no arrows, a swipe turns the month, always as tall as a six week month so the sheet never changes height, a gap and a line between two months mid swipe, only the month shown and the two next to it kept, the one in the direction last swiped made first; workout days filled in ink, today ringed; next to the streak an outlined calendar-check button takes the calendar back to this month: it follows the carousel frame by frame, never a timer, showing as much as the month shown has moved from this one, its arrow on the side of this month and pointing to it, and until it is half in it takes no taps, focus or semantics); a workout day closes it and jumps the list to that day's workout, marked for a moment. On top, while a discarded workout can still be restored and none is running, a strip (`restore_strip.dart`) offers it in blue; Restore makes it the running workout and goes to the Workout tab. Empty and error states say what to do. The tab shell prebuilds History offstage ~1 s after launch so its first open is instant. `SessionDetailPage` (the past workout): back, title, an outlined Edit, and a menu only while the cubit can restore this very workout (`savedSessionId`, nothing running) holding Restore workout; the times ("Mon 9 Nov, 18:04 to 19:16"), length, gym and working volume ("5,540 kg lifted", warm-ups left out), the plan bar in ink with the working set count, then each exercise with "4 sets, 2 warm-ups" and its sets in shared columns (badge, weight, unit, times sign, reps, rating); a tap on an exercise folds it to "Best set 80 kg × 8" and back (`AnimatedReveal`, for as long as the page is open). `SessionEditPage` ("Edit workout") edits a draft (`SessionDraft`, in memory): Name, Gym, Started and Ended in an `ItemCard`, each in its own sheet (`EditSheet`, `showGymPicker`); the sets as outlined rows under their exercise, a tap opens one in place with steppers, the number entry from Settings and the effort strip, the badge toggles warm-up, two swipes delete, Add set copies the exercise's last set, Add exercise picks one (`ExercisePickerPage`) and starts from last time's top set; a changed row is outlined amber with an Edited (or New) tag and a "Was 80 kg × 8" line. Typed values keep the workout's rules (`requiredWeight`, `requiredReps`, `confirmWeightEntry`, `confirmRepsEntry`), and the stored kilograms stay untouched unless the shown value moved. Nothing is written until Save on the amber bar that slides up with the change count (Discard drops the draft); leaving with changes asks first. Delete workout is only in this page's menu, behind `showConfirmDialog`; it leaves both pages. Save keeps what the page does not edit (id, split day). Shell-level perf harness: `tracker/benchmark/history_first_open_device_test.dart` (profile, `flutter drive`: first open, the calendar sheet, a jump, month changes, a save while open). The keyboard in a sheet has its own: `tracker/benchmark/keyboard_sheet_device_test.dart` (profile, on an Android device or emulator, the real keyboard; `BENCH_APP=perframe` replays the old per-frame theme rebuild).
- **workout** - the Workout tab starts and runs workouts, nothing else. Every workout screen docks its one next step at the bottom in a `WorkoutDock` (Start, Continue, Log, Next, Finish workout), so that step is always in the same place. `WorkoutPage` shows `StartView` when idle (the split's name, a tap opens the "Train from" sheet: another split to train from for this visit without making it current, and last of all an Empty workout row ("Pick exercises as you go") that starts a workout without a plan; its days as a row of chips that scrolls sideways when they do not fit and opens on the one that is Up next; the open day below with when it was last done and how long it took, the empty plan bar and its exercises, each with its target and last time's top set; a tap on another chip opens that day in place; no restore here (`WorkoutCubit` keeps `restoreLastWorkout` for History to offer later); the dock: the gym the workout starts at, home unless picked, with Change, over Start, which starts the open day) and `WorkoutOverview` during a workout (live timer, gym chip, quiet Finish, menu with Change gym / Discard workout, the plan bar, the exercises in order with a right-anchored "2 of 4" count: done ones shrink to their best set, the current one is outlined, waiting ones show their rep target and last time's top set, hold reorders, swipe removes; the dock: Continue the current exercise with the set it opens on ("Set 3") on the side, Finish workout once the plan is done). Starting a split day lands on its exercise list. Each exercise opens `ExercisePage`: a position strip (day, exercise n of m, clock, the plan bar; tap goes back), weight x reps rows prefilled in grey (`ghostForRow`; planned warm-ups open as warm-up rows) with last time's values small under each number, every row full width with its numbers in shared columns and its state on its frame (waiting = grey outline, a tap anywhere on it selects it; logged = tinted and ticked), the current row opened up with -/+ steppers, its set and rep target on the outline, how it compares with the same set last time on the outline's bottom edge ("2.5 kg more than last time", only when it differs) and an RPE / RIR strip (the usual values; the rest in `showEffortSheet`), save on leaving a row, badge tap = warm-up, two swipes = delete. Only the dock logs (the rating rides on the side of the Log button), then offers Next (the next exercise with sets left) or Finish workout, with the rest clock beside it (`WorkoutDock.leading`). `finishWorkout` (`finish_workout.dart`) shows what gets saved and which planned sets are open, and can discard the workout instead. Reps go from 0.1 to 2000 (`rep_limits.dart`); above 200 logging asks first (`confirmRepsEntry`). Field errors sit under their own field; the keypad slides in and out, and switching the set being done animates the rows. The gym sheet (`showGymPicker`) marks the gym in use; a gym added there asks for its name only. Number entry follows Settings: `NumberKeypad` overlay (default), the phone's decimal pad + `KeyboardToolbar`, or steppers (drag to scrub, hold to type). One bar runs through all three screens (`PlanBar`, `ui/core/ui/plan_bar.dart`, with `planSegments` in the workout's `plan_bar.dart`: a segment per exercise, as wide as its sets, filled as they are logged). `start_workout.dart` holds the start helpers (`startSplitDay`, `startEmptyWorkout`, `planOf`, `startGymOf`); `workout_entries.dart` the overview model (`WorkoutEntry`, `workoutEntries`, `nextEntryAfter`); `set_comparison.dart` words a set against last time's (`compareWithLast`).
- **exercises** - `ExercisesPage` master library (browse by muscle group or movement pattern), `NewExercisePage` for custom exercises, `ExerciseDetailPage` for profile + performance history (best normalized 1RM over time).
- **splits** - the Splits tab plans only (no start buttons). `SplitsPage` lists splits current first, then by last use (Make current slides the split to the top and the old current right below it, in a `SlidingColumn`; Current badge, menu: Rename (the name turns into a field in place, keyboard up, Done saves) / Make current / Duplicate / Delete; days reorder by grip, peek on hold or mouse hover, go in two swipes; unsaved-changes strip that opens and closes with the draft; New/Edited tags; removed days struck through with Restore); `showNewSplitSheet` creates a blank or template split straight away. `SplitDayEditorPage` edits a day (name, exercises reordered by grip and removed in two swipes, planned sets as equal chips in a grid edited in `showSetTargetSheet`: reps and warm-up or working, deleted in two swipes, removed exercises restorable) with a save bar that slides up while there are unsaved changes; `showReviewChangesSheet` lists every change (old struck through, new bold) before Save / Discard.
- **settings** - `SettingsPage` is a hub: one row per part of the app with settings, named and iconed like its tab and summing up what is set inside (`WorkoutSettingsPage`: number entry, prefill, effort rating, heavy weight check; `SplitsSettingsPage`: the rep target new exercises start at, edited in `showSetTargetSheet` without the warm-up switch, kept on close (`saveOnClose`) as well as on Done; `GymsPage`), then General (weight unit), then, in dev builds (`!isProd`) under a `TestModeScope`, Testing: the Test mode switch and, while it is on, Reset sample data. Test mode runs the app on `seedSampleData` in a throwaway database with in-memory saved state; the real database and saved state are kept aside, untouched, and it starts over on every launch. Every page is built from `settings_list.dart`: `SettingsScaffold` > `SettingsSection` (heading, outlined card, note) > `SettingsLinkItem` / `SettingsSwitchItem` / `SettingsChoiceItem` (opens `showChoiceSheet`: each option with what it does, one tap picks and closes) / `SettingsValueItem`. Card rows are inset 4 px on every side, so a pressed or selected highlight never touches a divider. A new setting is one row; a section that outgrows its page moves behind a link row. Only settings that change something are shown (`notificationsEnabled` / `analyticsEnabled` stay in the payload with no UI). `GymsPage`: create/edit gyms in `editGymSheet`, primary baseline multiplier locked to 1.0, auto-estimate via `estimateGymMultiplier`.
- **analytics** - every graph follows one exercise (no "All exercises"): Estimated 1RM (each session's best set, a line), 1RM PR (the best ever, a staircase that climbs only on a PR, other sessions faint dots), Heaviest weight (a line) or Volume (columns per week or month). `AnalyticsData` (`view_models/analytics_data.dart`) reads every session, exercise and gym once and works each series out once per range and day. `graph_readout.dart` holds the labels and the headline (`graphHeadline`: the newest value and how far it moved, "No new PR in 3 months", the last finished week with the average; while a point is read, its value, date and session, with a `RecordTag` on a PR). `GraphTile` (`graph_tile.dart`): exercise, short measure, headline, a sparkline; hover reads, a tap opens. `GraphPage`: the headline, the chart, `GraphRangeControl` (1M 3M 1Y All, shared with the Feed through Settings), then the sessions in range newest first (value, the set behind it, PR tag), each opening `SessionDetailPage`; its menu edits (`GraphEditor`) or deletes the graph. `GraphEditor.show` is an `EditSheet`: the exercise (`GraphExercisePickerPage`) and the measure, each with what it shows; the graph names itself. `GraphPanel` is a small headline over a chart for pages about something else: `ProgressionPage` (overall volume by month, best 1RM) and `ExerciseDetailPage` (best 1RM).

## Visual debugging screenshots (widget-test sweep)

`pwsh run-visual-tests.ps1` (repo root) renders every app page, dialog and sheet at 320x568, 800x600 and 1280x720 with real Inter text and Lucide/Material icon fonts, writing ~66 PNGs plus `manifest.json` to `tracker/build/test_screenshots/` (gitignored). Exit code = flutter test exit code. The sweep also runs on Linux CI via bare `flutter test`.

- **Vision-analysis loop** (for Claude Code, after UI changes): run the script -> read `manifest.json` (or glob `tracker/build/test_screenshots/*.png`) -> inspect the images with the Read tool for overflow, clipped text, misalignment or tofu glyphs -> fix -> re-run. Files suffixed `_FAIL` are auto-captures of the screen that threw a render exception; the test output's `SCREENSHOT-SWEEP:` / `SCREENSHOT:` lines map captures to pages.
- Under the hood: `test/ui/visual_screenshots/visual_screenshot_sweep.dart` (the sweep body) + one `visual_screenshots_<size>_test.dart` per size, `test/ui/overflow/layout_overflow_sweep.dart` + one `layout_overflow_<size>_test.dart` per extra window size (480x800, 640x720, 1920x1080 - the sweep's own 320x568/800x600/1280x720 already fail on render exceptions, so they have no overflow file; overflow assertions over the same pages; one file per size so each runs in its own process — libisar's native worker pool wedges multi-case sweeps on 4-CPU CI runners), and the shared infra in `testing/` (`screenshot_helpers.dart`, `test_fixtures.dart`, `test_fonts.dart`, `test_helpers.dart`). The output directory is disposable; `-NoClean` keeps previous captures.
